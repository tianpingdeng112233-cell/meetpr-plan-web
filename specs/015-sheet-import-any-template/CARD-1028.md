## 1. 识别完成页横向撑破（W1）

现象：结果摘要里有「没读懂的动作」块时，下方原表格子（含很多列）把 `section.import-dialog` 撑到 scrollWidth≈1900（clientWidth≈603）；自动滚到第一处红格时用了会滚动祖先的方式，整个弹窗横移，三格统计被拉宽、「需要注意的」右侧计数被挤出视口（截图 05/06/09）。失败周的原表格子块同理。

要求：弹窗宽度恒定（600–620，稿 ⑮–⑰）；原表格子在自己的容器里横向滚动（`overflow-x:auto`、`min-width:0`，长文本行折行或截断带 title）；自动定位只滚格子容器（`scrollIntoView({ block:'nearest', inline:'nearest' })` 作用于容器内，或手算 scrollLeft/Top），**不得**改变弹窗的 scrollLeft。

后端将修正 `INVALID_NUMBER.detail`（track 仅 intensity/weight，value 为原文），但前端也要兜底：`value` 为空或非字符串/数字时不拼「{值} 不是有效的数字」，改用 OTHER 的文案「这一行没读懂」；未知 `track` 同样兜底。

## 3. 导入后重载丢失暂存（W3，根因未知 → 按 /diagnose 六阶段）

现象：导入创建草稿后，编辑器显示「草稿 · 已自动保存 · N 个动作待填全或需修正（内容云端暂存中…）」，网络序列为 `PUT pending-revision`、`PUT`、`GET`、`GET`、`DELETE`(204)、`PUT`、`DELETE`(204)；最终库里 `plan_pending_revisions` 为空。切学员再重载后，教练在「同类写法」里选的「力竭」变回「—×—」，⚠ 计数消失（截图 07 → 16）。四次导入都是同一序列。

六阶段（必须按序，不得跳）：
1. **先造一条会红的命令**：在最高层 seam（`draftMirror-ui.test.tsx` / `ImportPlanDialog` 组件测试 / 编辑器 pending revision 相关 UI 测试，优先复用）写出「导入创建 → 有降级行 → 切走/卸载 → 重新挂载」后快照仍在、力竭仍在的用例，确认它红。没有这条红命令不准提假设。
2. 列 3–5 个可证伪假设（例如：创建后编辑器以「干净基线」挂载导致卸载清理删快照；导入流程的 reconcile 回调与 autosave 竞态；删除条件把「降级保存」误判为「全部已落库」；该问题在 main 上同样存在），写进 JOURNAL。
3. 不用 `git stash`，用 `git show main:<file>` 或临时 worktree 确认 main 上是否同样复现，结论写进 JOURNAL（决定这是不是 015 回归）。
4. **到此停下 W3**：红用例留在工作区（可 `it.fails`/`it.todo` 标注以免挡全量），假设交回 Opus 给 David 过目后另派修复。本卡其余项照常完成。
