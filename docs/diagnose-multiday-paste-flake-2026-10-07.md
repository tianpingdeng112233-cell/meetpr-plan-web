# 诊断：多日选择粘贴测试偶发红（2026-10-07）

状态：已修复。方案 A 于 2026-10-07 由 David 拍板，按文末修复卡实装，与本文件同一个 PR。
现场：`origin/main@f18ec2e`（比报告时的 `ea286db` 多一个 #104，涉事代码两处一致）。

## 结论

这是**测试与产品挂载逻辑之间的时序竞态，不是「多日选择下粘贴后选区没回到目标日」的产品 bug**。粘贴动作本身是对的；把选区改错的是编辑器挂载时排的一帧回调，它晚到了。

## 根因

`src/features/plan-editor/PlanEditor.tsx:963-981` 的「首次挂载定位到当前周」effect 用 `requestAnimationFrame`（下一帧回调，jsdom 里约 16ms 后触发）做两件事：滚到当前周，并**无条件**把选区设成当前周的第一个训练日（`setSel(target)` + `setDaySelection(singleDaySelection(target))`）。

失败用例（`multiday-selection-ui.test.tsx:387`）的步骤是：挂载 → 点行 → Cmd+C（让出一次）→ 选周二+周三 → Cmd+V（让出一次）→ 断言选区是 `1:1`。机器快时整段在 16ms 内跑完，帧回调还没触发就卸载了，绿。全量并发把 CPU 占满时，这段超过一帧，帧回调落在粘贴那次让出里，排在 `pasteRowsIntoSelection` 把选区设成 `1:1` **之后**，于是选区被改回第一个训练日 `1:0`，行数断言（404 行）照过、选区断言（405 行）红。

它是该文件里唯一同时满足「选中的不是第一个训练日」「之后有真实让出」「再断言选区」三条的用例，所以只有它中招。

## 证据

| 命令 / 探针 | 结果 |
|---|---|
| 全量 `npx vitest run` ×6 | 2 红 4 绿，红的都是这一条、同一断言 |
| 单文件串行 ×5 | 5/5 绿 |
| 单文件 16 进程并行（压 CPU） | 7/16 红 |
| 探针 V1：粘贴的 act 里真等 40ms | 确定性红，`['1:0']`，帧回调记录落在 paste 阶段 |

| 探针 V3：挂载后先等 40ms 让帧回调跑完，再操作 | 绿（帧回调落在 mount 阶段） |

## 假设排序与判决

1. **挂载帧回调晚到覆盖选区** — 成立（V1–V4 四个预测全中）。
2. 行 id 用 `Date.now()+performance.now()` 撞号导致行选区收敛到别的日 — 不成立：`clip-row` / `paste-row` 前缀不同不可能撞；且关掉帧回调即绿。
3. 拖拽的 `suppressDayClickRef` 定时器吞掉点日事件 — 不成立：那样红的应是 399 行（粘贴前选区），实际 399 过、405 红。
4. 剪贴板 mock 跨用例/跨文件泄漏 — 不成立：单文件即可复现，且泄漏会改粘贴内容而不是选区。
5. 与当天日期有关 — 不成立：同一时刻串行全绿、并行才红。

## 为什么 9/16 全量是绿的

帧回调自 8/10（`3119001`）就在，这条用例 7/31 写成、9/16（`d71a413`）并入 main，竞态从那天起就潜伏着，只是机器够快时碰不到。它跟代码改动无关，跟跑全量时机器有多忙有关；你那边 4 连红、我这边 2/6 红，差别我只能归到负载，没法进一步证实。

## 对真实用户的影响

基本没有。浏览器里帧回调在挂载后一帧内就跑完，人手点不进这个窗口。理论残留是：计划很大、首帧卡顿时，排队中的点击先于帧回调处理，选区会被弹回第一个训练日——只动选区、不动数据，概率极低。但同一竞态对其它 PlanEditor UI 测试是潜伏雷：任何「有真实让出 + 断言选区」的用例都可能在高负载下红。

## 修复卡（T1）

先读仓根 `CONTEXT.md` 与 `CLAUDE.md`。

**目标**：挂载时的帧回调不再覆盖用户已经做出的选区；高负载下全量稳定绿。

**文件范围**（仅这两个）：
- `src/features/plan-editor/PlanEditor.tsx`：只动 963-981 这个挂载 effect 的帧回调。
- `src/features/plan-editor/multiday-selection-ui.test.tsx`：加一条回归用例，不改现有用例。

**做法（方案 A）**：帧回调里设默认选区改成「尚无选区才设」——`setSel((current) => current ?? target)`，`setDaySelection((current) => current.anchor ? current : singleDaySelection(target))`。滚动定位照旧。

**约束**：
- 不改默认选区的时机（仍在帧回调里），不把它挪进 `useState` 初值——那会改变所有测试同步可见的初始状态。
- 不动粘贴逻辑、不动其它 `requestAnimationFrame` / `setTimeout` 调用点。
- 不用 fake timers 或全局 stub 去绕；修在源头。
- 不 commit / push；本仓没有 `docs/CODEX-JOURNAL.md`，不新建，交付说明与命令输出写在最终回复里。

**测试 seam**（先红后绿，复用现有文件的 `day` / `click` / `selectedDayKeys` 助手）：
新用例「挂载帧回调不覆盖已做出的选区」：渲染周一有训练行的一周 → 点周二 → 在 `await act(async …)` 里等一帧（`await new Promise(r => requestAnimationFrame(() => r(null)))`）→ 断言 `selectedDayKeys(host)` 为 `['1:1']`。修前确定性红（得到 `['1:0']`），修后绿。

**验收标准**：
1. 新回归用例修前红、修后绿，贴两次输出。
2. 上面那条 16 并行命令连跑 2 轮，32/32 为 `14+1 passed`（修前约四成红）。
3. `npx vitest run` 连跑 3 次全绿；`npx tsc --noEmit` 退出 0。
4. 不带选区直接挂载时，默认仍选中当前周第一个训练日（现有用例覆盖，不得改它们）。
5. diff 只含上述两个文件。

**Out of Scope**：其它文件的同类潜伏用例排查；测试层统一 rAF 策略；首屏默认选区的产品行为调整。
